## 一、问题的起点

前面实现了 Conversation History 后，`chat.py` 每轮把**完整历史**发给模型：

```python
messages.append({"role": "user", "content": text})
messages.append({"role": "assistant", "content": answer})
llm.chat(messages)          # ← 每轮都发全部历史
```

于是历史无限增长，带来三个问题：

| # | 问题 | 后果 |
| --- | --- | --- |
| ① | **Context Window 超限** | 请求直接失败 |
| ② | **token 成本上升** | 越来越慢、越来越贵 |
| ③ | **注意力被稀释** | 无关历史淹没关键信息，回答反而变差 |

> ⭐ **最重要的一句话：Context 越多，不代表 AI 越聪明。**

## 二、Challenge 2：滑动窗口（按条数裁剪）

### 2.1 不是简单的 `list[-N:]`

第一个直觉是 `messages[-6:]`，但这是错的。

**原因：`messages` 不是一串独立的字符串，而是一串有结构的关系。**

```
一轮完整对话 = user + assistant，必须成对出现
```

如果只留 `assistant` 而丢掉它对应的 `user`，模型看到的是：

> 一个**没有任何提问**的回答

这在语义上是残缺的，会让模型困惑甚至产生幻觉。

### 2.2 §11 那个设计问题的答案

> 问题：`[system, u1, a1, u2, a2, u3, a3]` 最多保留 4 条普通消息，应该是哪个？
>
> ```
> A: system + u2 a2 u3 a3          ← ✅ 正确答案
> B: system + a2 u3 a3             ← ❌ assistant2 没有对应提问
> ```

**答案：A。** 因为 `assistant2` 是对 `user2` 的回答，必须一起保留。

### 2.3 三条设计规则

| # | 规则 | 理由 |
| --- | --- | --- |
| ① | **system 永远保留** | 它是人设/规则，不属于"对话内容"；且在列表最前面，天然不在"最近 N 条"里 |
| ② | **不切开 user/assistant 对** | 成对才有意义 |
| ③ | **裁剪后首条必须是 user** | 历史的结构约定是"user 起头，交替出现" |

**关键洞察：规则 ② 和 ③ 可以用同一段代码满足** —— 只要"从第一条 user 开始切"：

```python
start = 0
while start < len(kept) and kept[start].get("role") != "user":
    start += 1
kept = kept[start:]
```

> 用 `while` 而不是 `if`：因为将来加了 `tool` 消息后，
> 开头可能**连续多条**都不是 user，一次判断处理不了。

### 2.4 实测结果（7 轮对话，窗口 = 6）

| 轮次 | 上下文 | 输入 token | 本轮裁剪 |
| --- | --- | --- | --- |
| 1 | 3 条 | 18 | — |
| 2 | 5 条 | 29 | — |
| 3 | 7 条 | 40 | — |
| 4 | 7 条 | **40** | 裁掉 2 条 |
| 5 | 7 条 | **40** | 裁掉 2 条 |
| 6 | 7 条 | **40** | 裁掉 2 条 |
| 7 | 7 条 | **40** | 裁掉 2 条 |

**token 从"一直涨"变成"平台期"** —— 这就是裁剪生效的物理证据。

### 2.5 ⚠️ 踩到的坑

**坑 1：`list[-0:]` 不是空列表**

```python
[1, 2, 3][-0:]     # [1, 2, 3]   ← 不是 []！
```

因为 `-0` 就是 `0`，而切片起点为 0 表示"从头开始"。

后果：如果不做防护，`--max-history 0`（本意"不传历史"）会变成"**传全部历史**"，完全反向。

```python
if max_messages <= 0:          # ← 这行不加就会出现上面的 bug
    return system_msgs
```

> 这类"**边界值语义反了**"的 bug 很危险 —— 它**不报错**，只是行为完全相反。
> **测边界值（0、负数、1）应该成为习惯。**

**坑 2：奇数窗口会浪费一个槽位**

| `max_messages` | 实际保留 |
| --- | --- |
| 4 | 4 |
| **5** | **4** ← 浪费 |
| 6 | 6 |
| **7** | **6** ← 浪费 |

原因：为保证"首条是 user"，奇数窗口的最后一条（assistant）会被丢掉。
**结论：窗口大小应该取偶数**（一轮本来就是 2 条）。

## 三、Challenge 3：Token 计数

### 3.1 核心认知：字符数 ≠ token 数

**实测数据**（真实 API 调用，已扣除模板开销 4 token）：

| 内容 | 字符数 | 真实 token | 每字符 |
| --- | --- | --- | --- |
| `你好` | 2 | 1 | 0.50 |
| `abcdefgh` | 8 | 2 | 0.25 |
| `你好世界`×2 | 8 | 4 | 0.50 |
| `1234567890` | 10 | 4 | 0.40 |
| `def hello():` | 12 | 3 | 0.25 |
| `{"role":"user","content":"hi"}` | 30 | 9 | 0.30 |
| `" " × 10` | 10 | **1** | 0.10 |
| 英文真实句子 | 65 | **9** | 0.14 |

**规律：**

| 类型 | 大约 token 密度 |
| --- | --- |
| 中文 | **1 token ≈ 2 个汉字** |
| 英文散文 | 1 token ≈ 7 个字符（常见词能整体合并） |
| 代码 / JSON | 1 token ≈ 3.3 个字符 |
| 空格 | 1 token ≈ 10 个空格（连续空白被合并） |
| 数字 | 1 token ≈ 2.5 个字符 |

### 3.2 ⚠️ 为什么要关心？—— 两个实测结论

**结论 1：即使什么都不问，每次请求也有固定开销**

```
content='x' → prompt_tokens = 5
其中模板开销 = 4
```

**结论 2：⭐ 同样是「1 条消息」，token 差 164 倍**

```
短消息 "嗯"                 1 字符  →    1 token
长消息（一段技术问题）    287 字符  →  164 token

两条都是「1 条消息」
```

**这就是 Challenge 2 那套策略的根本缺陷：**

> 用【消息条数】控制窗口 = 假设「每条消息差不多大」
> **这个假设是错的。**
>
> `max_messages=6` 可能意味着：
> - 6 条短消息 → 约 20 token（**浪费额度**）
> - 6 条长消息 → 约 1000 token（**照样超限**）

**正确的控制单位是 token。**

### 3.3 两种策略的端到端对比（实测）

同一组问题（Q1/Q5/Q6/Q7 很短，Q2/Q3 中等，**Q4 很长**）：

**策略 A：按条数（`--max-history 4`）**

```
预估  14 →  26 →  32 → 154 → 146 →  27 →  27    ← ⚠️ 剧烈波动
实际  14 →  25 →  29 → 105 →  99 →  24 →  24
上下文始终 5 条，只保留 2 轮
```

**策略 B：按 token（`--max-tokens 300`）**

```
预估  14 →  26 →  48 → 181 → 196 → 210 → 224
实际  14 →  25 →  41 → 127 → 136 → 146 → 156    ← 平滑上升且在预算内
上下文 3 → 5 → 7 → 9 → 11 → 13 → 15 条，保留了全部 7 轮
```

**策略 C：两个都开（先按条数粗剪，再按 token 精剪）**

```
预估  14 →  26 →  46 → 179 → 182 → 182 → 171
实际  19 →  27 →  42 → 128 → 128 → 131 → 127    ← 最稳定
上下文稳定 9 条
```

### 3.4 对比结论

| | 按条数（A） | 按 token（B） |
| --- | --- | --- |
| token 量 | **24 ~ 105，波动 4.4 倍** | 平滑，压在预算内 |
| 保留历史 | 固定 2 轮 | **全部 7 轮**（短消息时） |
| 可预测性 | ❌ 差 | ✅ 好 |
| 预算利用率 | 有时浪费（24/300） | 有时浪费（因估算保守） |

> ⭐ **A 的问题不是"裁得多"，而是"不可预测"。**
> 24 token 和 105 token 都算"4 条"，你无法凭条数预估成本。

### 3.5 实现：`trim_by_tokens()`

规则和按条数版本**一致**（①②③ 是语义约束，与策略无关），**新增一条**：

> **④ 最新的那条消息必须保留，哪怕它单独就超预算**

因为最新消息 = 用户当前的问题。裁掉它的话，模型收到的历史里没有"要回答什么"，完全答非所问。

```python
kept = []
used = 0
for msg in reversed(dialog):
    cost = _message_cost(msg)
    # kept 为空 = 正在处理最新那条 → 无条件装进去（规则 ④）
    # kept 非空 = 处理更早的消息 → 装不下就停
    if kept and used + cost > budget:
        break
    kept.append(msg)
    used += cost
```

> `if kept and ...` 这个条件很微妙：**靠 `kept` 是否为空来区分"最新那条"和"更早的"**。

## 四、⭐ token 估算器：为什么必须估算，以及误差有多大

### 4.1 为什么不能精确计算？

裁剪发生在**每一轮、发请求之前**。为了数 token 而先发一次请求 —— **那本身就要钱要时间**，逻辑上不成立。

**工业界的标准做法是「两套账」：**

```
① 本地估算 → 做【预算决策】   快、免费、有误差
② API 的 usage → 做【精确记账】准、但事后才知道
```

### 4.2 实测校准的系数

```python
_TOKENS_PER_CJK_CHAR = 0.5     # 中文
_TOKENS_PER_WS_CHAR = 0.05     # 空白
_TOKENS_PER_OTHER_CHAR = 0.28  # 其他（ASCII/代码）
_TOKENS_PER_MESSAGE_OVERHEAD = 4   # 每条消息的结构开销
```

### 4.3 ⚠️ 误差是真实存在的，而且无法消除

**校准过程**（拿 16 个实测样本反推）：

| 系数方案 | 平均绝对误差 | 高估 / 低估 |
| --- | --- | --- |
| cjk=0.6, other=0.3 | 34.0% | 7 / 3 |
| cjk=0.5, other=0.3 | 30.5% | 5 / 3 ← **选用** |
| cjk=0.5, other=0.25 | **24.4%** | 3 / **6** ← 误差最小但低估多 |
| cjk=0.45, other=0.28 | 29.5% | 3 / 6 |

**冲突点：误差最小的方案反而低估更多。**

### 4.4 ⭐ 关键工程决策：安全优先于精确

> **为什么刻意选择"高估"的方案，而不是误差最小的？**
>
> | | 高估 | 低估 |
> | --- | --- | --- |
> | 后果 | 多裁掉一点历史 → "记性差一点" | 请求超出模型窗口 → **直接报错失败** |
> | 严重性 | 可接受 | **不可接受** |
>
> **所以宁可高估。这是「安全优先于精确」的工程取舍。**

**实测验证**（端到端对比数据）：

```
策略 B:  预估 224 / 实际 156  → 高估 44%
策略 C:  预估 171 / 实际 122  → 高估 40%
```

符合预期 —— 估值偏保守，实际用量约为预算的 52%。

**代价：预算利用率低**（156/300 = 52%），即"为了安全少记了一些历史"。

### 4.5 误差为什么无法靠调系数消除

因为 **BPE 分词的粒度不是线性的** —— 取决于"这段文字在词表里有没有现成的 token"：

| 文本 | 每字符 token | 原因 |
| --- | --- | --- |
| 真实英文句子 | 0.14 | 常见词能整体合并成 1 个 token |
| 随机字母 `abcdefghijklmnop` | 0.375 | 没有现成 token，要拆 |
| 10 个空格 | 0.10 | 连续空白合并 |

**同一个字符，在不同上下文里的 token 数不同。**
所以线性估算**本质上就不精确**，±30% 是可接受的代价。

> **要精确就必须用真正的分词器**（`tiktoken` / `transformers` 的 tokenizer），
> 但那要下载词表（几十 MB）+ 额外依赖。**是否值得，取决于场景。**

## 五、遗留问题（下一个要解决的问题）

### 5.1 裁剪是「永久」的

```python
messages = trim_by_tokens(messages, args.max_tokens)   # 重新赋值
```

被裁掉的历史**真的没了**，`/history` 也看不到。

**真实产品更常用：保留完整历史，只裁"发出去的那份副本"**

```python
full_history.append(...)                          # 完整存着
to_send = trim_by_tokens(full_history, budget)    # 只裁副本
llm.chat(to_send)
```

| | 我当前做法 | 保留完整历史 |
| --- | --- | --- |
| 内存 | 省 | 多占 |
| `/history` | 只看得到窗口内 | 全程可见 |
| 以后做总结 / 抽 Memory / 检索旧对话 | ❌ 数据没了 | ✅ 有数据 |

> ⭐ 后面学 **Summarization** 时，**要总结旧历史的前提是你还留着旧历史** ——
> 那时会自然地回到方案 2。

### 5.2 滑动窗口的根本缺陷

不管按条数还是按 token，滑动窗口都是**「越旧越不重要」**的假设。

**但事实常常不是这样：**

```
第 1 轮：  我叫 Jack，是 Java 开发
...（50 轮无关对话）
第 51 轮： 帮我写个 Spring Boot 的 Controller

→ 窗口里早就没有"我是 Java 开发"了
→ 模型给出 Python 的示例
```

**真正重要的信息不一定在最近** —— 这就通向两个后续方向：

```
                    Context Management
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   截断历史            压缩/总结             检索
  Truncation          Summarization       Retrieval
                    （留下信息）          ⭐ RAG 的动机
```

### 5.3 Memory ≠ messages

```
messages          = 当前请求携带的上下文（易失、有窗口限制）
Memory            = 持久化的结构化信息
                    name = Jack
                    language = Java
                    framework = Spring Boot
```

```
Memory ──▶ Context Builder ──▶ Prompt ──▶ LLM
```

> 这是后面 Agent 系统的重要架构：**记忆是存起来的，上下文是每轮拼出来的。**

## 六、面试题

**Q1：Conversation History 为什么不能无限增长？**

三个原因：① 模型的 Context Window 有硬上限，超了直接失败；② 每轮都要重发全部历史，token 数累加，成本和延迟快速上升；③ 无关历史会稀释注意力，反而让回答质量下降。

**Q2：用「保留最近 N 条消息」做裁剪有什么问题？**

条数是 token 的很差近似。实测同样 1 条消息可以是 1 token 也可以是 164 token，所以固定条数无法控制成本 —— 短消息浪费额度，长消息照样超限。正确做法是按 token 预算裁剪。

**Q3：裁剪历史时必须遵守哪些约束？**

① system 消息必须保留（它是人设，丢了等于换人）；② 不能切开 user/assistant 对，否则模型会看到"没有提问的回答"，语义残缺；③ 裁剪后首条应为 user；④ 最新的用户消息必须保留，否则答非所问。

**Q4：为什么不能调用 API 来精确计算 token 数？**

因为裁剪是发送前就要做的决策，为了计数而先发请求本身就是成本。正确做法是本地估算做预算决策 + 用 API 返回的 usage 做事后精确记账。

**Q5：token 估算器的误差应该偏哪个方向？**

偏**高估**。高估只是多裁一点历史（"记性差一点"），低估会导致请求超出模型窗口而失败。这是"安全优先于精确"的取舍。

**Q6：滑动窗口的根本局限是什么？**

它假设"越旧越不重要"，但真正重要的信息（用户身份、项目约束）往往出现在很早的位置。根本解法不是截断，而是**检索**：用相关性而不是时间来决定保留什么 —— 这就是 RAG 的动机。
